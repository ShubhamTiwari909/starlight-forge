# Astro + Starlight generation

Use the current official Astro and Starlight documentation linked in `docs/research.md` when choosing versions, setup commands, config, or deployment instructions. Do not assume dependencies are installed or scaffold into an existing project without inspecting it.

## New project

When no suitable Astro project exists, propose a dedicated output directory and use the current official Starlight setup path (currently `npm create astro@latest -- --template starlight`, `pnpm create astro --template starlight`, or the Yarn equivalent). Scaffold only after the user has chosen website mode and the destination is safe. Review generated content before editing. Do not run package installation scripts without assessing risk. Add only the current Astro/Starlight requirements found in official docs; verify them at use time.

## Existing project

Read the existing `astro.config.*`, package manifest, content collections, and scripts. Integrate with the existing `starlight()` integration when appropriate. Preserve current site behavior and config. If the project is Astro but not Starlight, explain the changes and avoid replacing config wholesale.

## Content and navigation

- Starlight content is ordinarily under `src/content/docs/`; use `.md` for plain Markdown and `.mdx` only when JSX components materially help.
- Each page needs a `title` frontmatter value; a `description` improves metadata and search results.
- Use the `starlight.sidebar` configuration in Astro config for explicit groups/links, or suitable autogenerated navigation. Do not maintain both without a reason.
- Starlight provides built-in search and accessible responsive documentation UI. Avoid adding search libraries or custom UI without a specific need.
- Use code fences, meaningful headings, alt text for images, and relative source/document links. Treat embedded HTML/MDX from repository sources as untrusted; do not copy unsafe embeds.
- Keep application docs distinct from framework-generated template pages. Remove irrelevant starter pages only after confirming they are part of the new scaffold, never from an existing site without review.

## Verify and hand off

Inspect the exact scripts in the manifest before running them. When dependencies are present and trusted, use the site's declared build command; otherwise report why the build was skipped and what is needed. Verify navigation slugs and local links. Document the local dev/preview/build commands and static output location from current config. Give general deployment guidance only; never deploy or create hosting resources without explicit authorization.

`assets/templates/starlight-page.md` provides a minimal frontmatter example. It is not a complete or version-pinned site scaffold.
